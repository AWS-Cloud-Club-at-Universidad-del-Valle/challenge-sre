# CDK pivot: one-command EC2 that auto-boots the observability stack

The lab moves from "set it up locally / provision EC2 by hand with the AWS CLI" to "run AWS CDK and the whole stack comes up on one EC2". A new `cdk/` Python CDK v2 app provisions a single t3.small Amazon Linux 2023 instance whose cloud-init user-data installs Docker, pulls the lab code from a CDK S3 asset, writes a `.env` with `OTEL_ENABLED=true`, and runs `docker compose up -d` so every service (api, service-b, Prometheus, Loki, Alloy, Grafana, node_exporter, OTel Collector, Jaeger) boots unattended. The two Spanish tutorials were rewritten CDK-first and the Docker Compose stack, apps, and config are reused untouched. Tracing stays 100% OpenTelemetry → Collector → Jaeger with no X-Ray.

Watch for: nothing blocking. The egress rule shows `0.0.0.0/0` in the template but that is the default all-outbound rule, not an ingress hole (confirmed). The instance `.env` ships `GF_SECURITY_ADMIN_PASSWORD=changeme` — fine for a teaching lab, worth a mental note (confirmed).

**Verdict**: APPROVED

## High-level view

The CDK app is a single self-contained stack. `app.py` wires account/region from the ambient CDK environment with the pre-verified lab values as fallback and tags everything `Project=obs-lab`; `ObsLabStack` builds the VPC lookup, security group, IAM role, instance, S3 code asset, and user-data. The design choice that carries the pivot is code delivery by `aws_s3_assets.Asset` rather than git clone or heredocs — the student never `scp`s anything and the bundle is versioned with the stack.

The security posture is least-privilege and verified against the synth output: ingress is only 22/3000/8000 and only from the caller's `allowedCidr` (a required context value with a helpful error that points at `checkip.amazonaws.com`); the observability backends on 9090/3100/4317/4318/16686 stay on the internal docker network and are reached by SSM port-forward or an SSH tunnel. The IAM role carries only `AmazonSSMManagedInstanceCore` plus asset read — no X-Ray permission.

Tracing is unchanged from the locally-verified stack: OTel SDK → OTel Collector (`otlp` exporter) → `jaeger:4317`, with `COLLECTOR_OTLP_ENABLED=true` on Jaeger. The only X-Ray text anywhere is the one-paragraph "why not X-Ray" rationale in tutorial 02 section 4; the synth template and tutorial 01 contain zero X-Ray references.

The two tutorials plus README are the only docs. Tutorial 01 is the CDK deploy path (profile → bootstrap → allowedCidr → synth/deploy → verify containers → build the CPU and API dashboards → cost/security → destroy); tutorial 02 builds on the already-deployed infra for trace exploration. The dashboard PromQL references metric names that exist in `app/metrics.py`, so nothing is fabricated. The pivot was validated with `cdk synth` only; `cdk.out/` exists locally and is gitignored, and no CloudFormation stack was deployed.

### Code delivery via CDK S3 asset, boot via user-data

The stack bundles the repo root as an `aws_s3_assets.Asset`, excluding `.git`, venvs, caches, `.env`, `.agents`, `cdk/cdk.out`, `cdk/.venv`, and `node_modules`, then `asset.grant_read(instance.role)` grants the instance least-privilege read on exactly that object. User-data interpolates `asset.s3_bucket_name` / `asset.s3_object_key` into an `aws s3 cp` that lands in `/tmp/lab.zip`, unzips to `/opt/obs-lab`, writes the `.env`, and runs `docker compose build && docker compose up -d`.

```
CDK (Python) --> CloudFormation --> EC2 (cloud-init user-data)
                                      |-- dnf install docker + compose plugin
                                      |-- aws s3 cp <asset> ; unzip -> /opt/obs-lab
                                      |-- write .env (OTEL_ENABLED=true)
                                      '-- docker compose up -d  (all 9 services on obsnet)
```

The script runs under `set -euxo pipefail` and the extracted user-data passes `bash -n` (confirmed). The compose plugin is pinned to `v2.29.7`. User-data overwrites `/opt/obs-lab/.env` back to defaults on any re-run, so a student who edits the Grafana password on the box loses it if cloud-init re-fires — a known trade-off of the boot-to-known-state design, not a defect.

### Least-privilege security group and SSM-first access

Verified against `cdk.out/ObsLabStack.template.json`: ingress is three rules, all `CidrIp: 203.0.113.9/32` (the test `allowedCidr`), on ports 22, 3000, 8000. Port 8000 is gated behind `openApiPort` (default true). The backend ports 9090/3100/4317/4318/16686 have no ingress rule at all. Egress is the single default `0.0.0.0/0 / -1` all-outbound rule — this is the only `0.0.0.0/0` in the template and it is egress, not an ingress gap.

`allowedCidr` is a required context value; omitting it raises a `ValueError` whose message tells the student to pass `-c allowedCidr=$(curl -s https://checkip.amazonaws.com)/32`. The IAM role attaches only `AmazonSSMManagedInstanceCore`, so Session Manager works without opening SSH; `keyName` defaults to the existing `ec2-docker-api-key` and `-c keyName=""` drops the key pair for SSM-only access.

### No X-Ray anywhere except the rationale paragraph

`grep -ci x-ray` is 0 in the synth template and 0 in tutorial 01. Tutorial 02 has six matches, all inside section 4 ("Por qué OpenTelemetry + Jaeger y no X-Ray"): the index entry, the header, and the four-line rationale. The IAM role has no X-Ray managed policy or inline permission. The OTel Collector config exports via `otlp` to `jaeger:4317` (no native jaeger exporter, correct for contrib 0.109), and Jaeger runs with `COLLECTOR_OTLP_ENABLED=true`.

### CDK-centric tutorials, dashboards grounded in real metrics

Tutorial 01's section order matches the plan: objectives, architecture (Mermaid CDK→CloudFormation→EC2→Compose), CDK-only approach, prerequisites, `stay` profile, `cdk bootstrap`, obtain IP + `allowedCidr`, `cdk synth`/`cdk deploy`, verify user-data finished and containers `Up` (SSM/SSH + `docker ps` + `/var/log/cloud-init-output.log`), access Grafana by public IP, build the CPU dashboard, build the API dashboard, traffic, verification, troubleshooting, security, cost, `cdk destroy`.

The CPU dashboard uses `100 - (avg by(instance)(rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)` and explicitly distinguishes node_exporter (OS-level, inside the instance) from CloudWatch (hypervisor-level, managed) so students don't conflate the two sources. The API dashboard covers req/s, per-endpoint requests, p50/p90/p99 via `histogram_quantile` on `api_request_duration_seconds_bucket`, 2xx/4xx/5xx via `api_requests_by_status_class_total`, per-HTTP-code counts, and an error-rate panel. Every metric name in the PromQL (`api_requests_total`, `api_requests_by_status_class_total`, `api_request_duration_seconds`) exists in `app/metrics.py` — the dashboards are not fabricated against invented metrics.

Tutorial 02 documents Jaeger access with the exact `AWS-StartPortForwardingSession` SSM command to 16686 and the `-L 16686:localhost:16686` SSH alternative, then walks a trace with a shared `trace_id` and parent-child spans across api and service-b. The student IP is always obtained via `curl -s https://checkip.amazonaws.com`; the public IP is referenced as the `<PublicIp>` CfnOutput token, never a bare fabricated address.

### Synth-only, core stack untouched

`git diff` shows no changes to `docker-compose.yml`, `app/`, `service-b/`, `config/`, `scripts/`, or `tests/` — the locally-verified stack is reused as-is. `.env.example` keeps `OTEL_ENABLED=false` for the offline appendix and gains a one-line comment noting the EC2 `.env` is generated with `OTEL_ENABLED=true`. `cdk/cdk.out/` and `cdk/.venv/` are gitignored; the only committed CDK artifact beyond source is `cdk.context.json` (the cached VPC lookup), which is the normal, intended way to make `from_lookup` deterministic. No CloudFormation stack was deployed.
