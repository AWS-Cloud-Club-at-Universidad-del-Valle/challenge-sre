## Decision 1 — Code-delivery mechanism for user-data: CDK S3 asset (`aws_s3_assets.Asset`)
**Chosen:** bundle the repo (lab code: `app/`, `service-b/`, `config/`, `scripts/`, `tests/`,
`docker-compose.yml`, `.env.example`) as a single CDK `aws_s3_assets.Asset` directory. `cdk deploy`
uploads it to the CDK bootstrap bucket; user-data pulls it with `aws s3 cp` (the instance role is
granted read on that asset) and unpacks it into `/opt/obs-lab`, then runs `docker compose up -d`.
**Why:** the whole lab is ~160 KB, far under asset limits; no public Git repo is required; the
student never `scp`s anything (hard requirement); it is fully reproducible and versioned with the
stack. CDK auto-grants the asset read via `asset.grant_read(role)` and exposes `asset.s3_object_url`.
**Rejected alternatives:** (a) baking every file into user-data as heredocs — brittle, bloats
user-data past readability, easy to drift from the real files; (b) `git clone` — needs a public repo
and network to GitHub, and the repo may be private. The asset approach is the most reproducible and
is the PREFERRED option named in the task. Keep a one-line fallback note in the tutorial: if the
asset download fails, students can inspect `/var/log/cloud-init-output.log`.

## Decision 2 — CDK language: Python CDK v2
Keep the repo single-language (the apps are Python). `cdk/` is a self-contained Python CDK v2 app
(`aws-cdk-lib` v2 + `constructs`). Pin `aws-cdk-lib` and `constructs` in `cdk/requirements.txt`.

## Decision 3 — AMI resolution: `ec2.MachineImage.latest_amazon_linux2023()`
Resolves the latest AL2023 x86_64 AMI via the SSM public parameter at synth/deploy time (matches
the existing tutorial's SSM approach). t3.small is x86_64, so default CPU type is correct.

## Decision 4 — Access: SSM-first, SSH optional
Attach `AmazonSSMManagedInstanceCore` to the instance role so students can use SSM Session Manager
(and `aws ssm start-session` port-forwarding to Jaeger 16686) WITHOUT opening SSH. Key pair is a
context param defaulting to the existing `ec2-docker-api-key`; passing `-c keyName=""` (empty) omits
it (SSM-only). SG opens 22 only as a convenience, still scoped to `allowedCidr`.

## Decision 5 — Keep docker-compose.yml unchanged; set OTEL_ENABLED=true on the instance
The compose file already runs both locally and on EC2. Tracing is gated by `OTEL_ENABLED`; user-data
writes `/opt/obs-lab/.env` with `OTEL_ENABLED=true` so traces are on by default on the instance.
`docker-compose.yml` itself needs NO change. (`.env.example` keeps `OTEL_ENABLED=false` for the local
offline appendix; the EC2 `.env` is generated by user-data.)

### User-data script outline (cloud-init, idempotent, logs to /var/log/cloud-init-output.log)
```
#!/bin/bash
set -euxo pipefail                       # -x so every step shows in cloud-init-output.log
dnf update -y
dnf install -y docker unzip awscli       # awscli present on AL2023; install if missing
systemctl enable --now docker
usermod -aG docker ec2-user
# docker compose v2 plugin
mkdir -p /usr/local/lib/docker/cli-plugins
curl -SL "https://github.com/docker/compose/releases/download/v2.29.7/docker-compose-linux-x86_64" \
  -o /usr/local/lib/docker/cli-plugins/docker-compose
chmod +x /usr/local/lib/docker/cli-plugins/docker-compose
# fetch lab code from the CDK asset bucket (region-aware)
mkdir -p /opt/obs-lab
aws s3 cp "s3://<asset_bucket>/<asset_key>" /tmp/lab.zip --region <region>
unzip -o /tmp/lab.zip -d /opt/obs-lab
# .env with tracing ON by default
cat > /opt/obs-lab/.env <<'ENV'
GF_SECURITY_ADMIN_PASSWORD=changeme
OTEL_ENABLED=true
OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector:4317
LOAD_TEST_RATE=3
LOAD_TEST_DURATION=60
ENV
# idempotent bring-up
cd /opt/obs-lab
docker compose pull || true
docker compose build
docker compose up -d
```
- Values `<asset_bucket>`, `<asset_key>`, `<region>` are injected from the stack (Decision 1).
- Idempotent: re-running cloud-init re-copies and `docker compose up -d` is a no-op if already up.
- The CDK bundles the asset as a zip automatically ONLY when the asset is a single file; for a
  directory asset CDK produces a zip and `asset.s3_object_key` points at it — `unzip` is correct.
  (Implementer: confirm the asset packaging is `ZIP`; `aws_s3_assets.Asset` on a directory zips by
  default. If CDK produces a non-zip, adjust the extract command accordingly.)
